💬 主題一：意見分歧的溝通處理

跨部門溝通 Apple HIG UI/UX

面試官提問：「請分享一次你與 PM 或設計師在需求或 UX 上意見不合的經驗，你最後如何解決？」

情境 (Situation)

在開發統一數網包裹追蹤 App 時，設計師為了追求極致的扁平化，希望將包裹清單卡片的陰影 (Drop Shadow) 與邊框完全拔除，只靠輕微的背景色差來區分。

任務 (Task)

我放進實機測試後發現，在戶外反光或深色模式下，沒有陰影的卡片會失去視覺層級，導致使用者難以辨識可點擊區域。我必須說服設計師修改，但不能讓他覺得我是技術本位在拒絕。

行動 (Action)

我沒有直接打槍，而是將畫面 Build 到實機上讓他親自感受。接著，我帶入 Apple HIG 關於「層級深度 (Depth)」與「清晰度 (Clarity)」的規範，解釋 iOS UI 需要 Z 軸概念來建立操作直覺。

為了尊重他的美學，我主動提出折衷方案：利用程式碼調出一個擴散半徑極大、但透明度極低 (Alpha 5%) 的「彌散陰影」，或者加上 0.5pt 的極細邊框。

結果 (Result)

設計師看了實機 Demo 後非常滿意這個折衷方案。這不僅解決了辨識度問題，更建立了這個專案的標準 UI Component。這證明了用實機展示與官方 HIG 規範是化解主觀美學衝突的最佳利器。

🏗 主題二：技術債與架構重構

架構決策 Flutter to Native MVVM

面試官提問：「請分享一次你主動推動技術重構或優化架構的經驗。」

情境 (Situation)

我在統一數網主導專案時，舊版 App 是用 Flutter 寫的。除了 UI 渲染偶有掉幀外，最嚴重的技術債是「SDK 依賴地獄」。每年 iOS/Android 系統升級，都會導致依賴的第三方 Flutter 套件損壞，引發無法掌控的 Crash。

任務 (Task)

為了徹底奪回 App 穩定性的控制權，並償還舊有程式碼「商業邏輯與 UI 高度耦合」的技術債，我主導了將專案從 Flutter 全面轉回 iOS 原生開發的重構計畫。

行動 (Action)

在技術轉型上，我依據模組複雜度彈性選用架構。針對最核心、狀態最複雜的「包裹追蹤功能」，我全面導入 MVVM 架構，將批次 API 請求、物流狀態轉換等核心商業邏輯，全部抽離到 ViewModel 中保護起來。

同時，直接採用原生 API 捨棄跨平台 Bridge，徹底排除了套件不相容的定時炸彈。

結果 (Result)

重構上線後，因為第三方 SDK 導致的 Crash 幾乎降到零。更重要的是，包裹追蹤的商業邏輯變得極度清晰且可測試，未來增加新物流規則時，再也不用擔心改壞 UI，大幅提升團隊開發效率與產品穩定性。

🔥 主題三：最大挫折與生產環境事故

問題排查 Data Race Swift Actors

面競爭提問：「你犯過或處理過最大的技術錯誤是什麼？你怎麼解決？」

情境 (Situation)

我們遇過一個非常棘手的線上事故：Crashlytics 偶爾會收到崩潰警報，但在本地端極難重現。追查後發現，是因為背景的 API 輪詢與使用者的 UI 操作，在同一時間對同一份資料進行了讀寫操作。

任務 (Task)

這是一個典型的競爭條件 (Data Race) 造成的 Crash。我的任務是必須在不影響整體效能的情況下，徹底根除這個多執行緒併發問題，確保資料的一致性與執行緒安全 (Thread Safety)。

行動 (Action)

我先利用 Xcode 的 Thread Sanitizer (TSan) 成功重現問題。在評估解法時，我放棄了容易造成死結 (Deadlock) 且難以維護的傳統 Lock。

相反地，我決定導入 Swift 現代併發模型的 Actor 來重構該模組。利用 Actor 自動隔離狀態的特性，在編譯期就保證了同一時間只有一個任務能存取資料。

結果 (Result)

重構上線後，該 Data Race 造成的 Crash 徹底歸零。同時，程式碼的易讀性大幅提升，未來擴充業務邏輯時，再也不用擔心會不小心踩到多執行緒的雷。*(面對高頻率同步讀取，我也懂得搭配 @MainActor 或 Combine/AsyncStream 推播來兼顧效能)*。

🤝 主題四：Mentor 與跨端 Code Review

團隊協作 CI/CD SwiftLint

面試官提問：「你目前是一人開發 iOS，那你怎麼做 Code Review？如何確保程式碼品質？」

情境 (Situation)

雖然我目前是團隊唯一的 iOS 原生工程師，但我們有嚴格的跨端協作流程。我的 PR 必須由技術主管和 Android 工程師共同 Review 才能 Merge。

任務 (Task)

我的任務是：第一，確保自己不會因為一人開發而產出有盲點的程式碼；第二，擔任 iOS 領域專家，在 Review 時跨越語言隔閡，確保雙平台架構一致並符合商業邏輯。

行動 (Action)

我建立了「三道防線」的 Code Review 機制：
1. 自動化黑臉：在 CI/CD 中掛載 SwiftLint，自動攔截排版與命名不合規的 PR。
2. 跨端架構對齊：與 Android 工程師 Review 時，專注討論邏輯簡化與雙平台變數命名的一致性（例如將 Actor 的概念翻譯成 Mutex）。
3. 商業邏輯把關：最後由技術主管針對 PM 需求與測試狀態進行總體確認。

結果 (Result)

這套流程讓我不會淪為閉門造車。透過跨端協作，我的邏輯思維變得更洗鍊，且負責的 App 上線後穩定度極高，幾乎沒有雙平台行為不一致的 Bug，也證明了我具備在團隊中推動與建立標準的能力。
