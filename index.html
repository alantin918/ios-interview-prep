🔥 主題三：最大挫折與生產環境事故

問題排查 Data Race Swift Actors

面競爭提問：「你犯過或處理過最大的技術錯誤是什麼？你怎麼解決？」

情境 (Situation)

我們遇過一個非常棘手的線上事故：Crashlytics 偶爾會收到崩潰警報，但在本地端極難重現。追查後發現，是因為背景的 API 輪詢與使用者的 UI 操作，在同一時間對同一份資料進行了讀寫操作。

任務 (Task)

這是一個典型的競爭條件 (Data Race) 造成的 Crash。我的任務是必須在不影響整體效能的情況下，徹底根除這個多執行緒併發問題，確保資料的一致性與執行緒安全 (Thread Safety)。

行動 (Action)

我先利用 Xcode 的 Thread Sanitizer (TSan) 成功重現問題。在評估解法時，我放棄了容易造成死結 (Deadlock) 且難以維護的傳統 Lock。

相反地，我決定導入 Swift 現代併發模型的 Actor 來重構該模組。利用 Actor 自動隔離狀態的特性，在編譯期就保證了同一時間只有一個任務能存取資料。

結果 (Result)

重構上線後，該 Data Race 造成的 Crash 徹底歸零。同時，程式碼的易讀性大幅提升，未來擴充業務邏輯時，再也不用擔心會不小心踩到多執行緒的雷。*(面對高頻率同步讀取，我也懂得搭配 @MainActor 或 Combine/AsyncStream 推播來兼顧效能)*。

情境 (Situation)

雖然我目前是團隊唯一的 iOS 原生工程師，但我們有嚴格的跨端協作流程。我的 PR 必須由技術主管和 Android 工程師共同 Review 才能 Merge。

任務 (Task)

我的任務是：第一，確保自己不會因為一人開發而產出有盲點的程式碼；第二，擔任 iOS 領域專家，在 Review 時跨越語言隔閡，確保雙平台架構一致並符合商業邏輯。

我建立了「三道防線」的 Code Review 機制：

2. 跨端架構對齊：與 Android 工程師 Review 時，專注討論邏輯簡化與雙平台變數命名的一致性（例如將 Actor 的概念翻譯成 Mutex）。

🏗 關卡二：系統設計 (iGaming 賽事直播 App)

System Design MVVM / TCA AVFoundation Memory Management

面試情境：「請設計一個體育即時賽事 App，上半部是 Live 直播，下半部是高頻跳動的即時賠率。如何規劃架構與防範 OOM？」

1. 架構選擇 (MVC/MVVM vs TCA)

採取務實的 MVC / MVVM 混合開發。對於靜態頁面使用 MVC 求快；核心賽事頁面全面導入 MVVM 解耦 UI 與商業邏輯。面對極端複雜的狀態機（如直播+賠率+結帳互相干擾），則提出 TCA (The Composable Architecture) 作為未來單向資料流的進階升級方案，展現評估技術成本的 Senior 思維。

2. 資料流與多執行緒 (Actor & @MainActor)

利用背景的 Custom Actor (如 SocketActor) 接收高頻 TCP/Socket 賠率，徹底防範 Data Race。接著透過 Combine/AsyncStream 進行降頻 (Throttle)，最後由標記為 @MainActor 的 ViewModel 安全且同步地驅動 UI 更新。透過編譯器自動切換執行緒，免去傳統 DispatchQueue.main.async 的繁瑣。

3. 影音客製化 (AVFoundation)

捨棄笨重的 AVPlayerViewController，改用底層的 AVPlayer 搭配 AVPlayerLayer 鋪在畫面最底層 (Z-Index:0)，讓 SwiftUI/UIKit 元件（跑馬燈、賠率按鈕）能自由疊加。並透過 KVO 監聽 timeControlStatus 來實作精準的 Buffering 動畫。

4. 防範 OOM (雙層快取與降採樣)

除了全面改用 async/await 消除 Closure 帶來的 Retain Cycle 危機外，針對大量圖片湧入，實作 LRU Memory Cache (NSCache) + Disk Cache (FileManager) 雙層機制。並在解碼階段導入 Downsampling (降採樣)，避免大圖直接撐爆 RAM。

🔥 關卡三：底層技術快問快答

Deep Dive ARC Concurrency UIKit
Q1: weak vs unowned 差異與 Retain Cycle？

兩者都不增加參考計數，用來打破循環強參照 (Retain Cycle) 防止記憶體洩漏。weak 是 Optional，物件釋放後安全變為 nil；unowned 假設對方活得比自己久，若存取已釋放物件會直接 Crash。實戰中為了極致穩定性，一律優先使用 weak。

Q2: Closure 時代 vs async/await 的 OOM 防範？

以往使用 Closure 極易漏寫 [weak self] 導致 View Controller 無法釋放。導入 async/await 結構化併發後，非同步程式碼變為線性執行，天然消滅了複雜的 Closure 嵌套與 Retain Cycle。同時配合 @MainActor，編譯器會自動保證切回主線程，大幅降低 Crash 風險。

Q3: setNeedsLayout vs layoutIfNeeded？

setNeedsLayout() 是異步的，只做重繪標記 (Flag)，適合批次更改屬性；layoutIfNeeded() 是同步的，強制系統立刻計算排版並重繪。在實作 AutoLayout 動畫時，需將 layoutIfNeeded() 放入 UIView.animate 區塊中以產生順暢漸變。
